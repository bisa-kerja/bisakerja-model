# Model Training Production Readiness Gaps

This document assesses production-readiness gaps for the **model-training side only** of Bisakerja Model API.

Backend API is a separate repository: <https://github.com/bisa-kerja/bisakerja-api>. Backend-generated OpenAPI/Prisma snapshots or handoff fixtures may be used as contract inputs, but Backend source is not part of this model repository.

## 1. Model Training Scope

The training model does not need to produce every public API response field directly.

### Model/training-owned outputs

For the CV Analyzer flow, model/training focuses on these core outputs:

1. `jobFitAlignment`
   - CV/profile fit score against a target role or job context.
   - Grounded alignment signals from skills, role, experience, and job requirements.

2. `atsFriendliness`
   - ATS readability and format-readiness score.
   - Detected parser/format/structure issues.

3. `overallImpression`
   - Global CV impression against a target role.
   - Short product-ready summary signal, not raw model logs.

4. `candidateReranking`
   - Ranking or scoring for Backend-provided candidate job IDs.
   - Model must not invent jobs or hydrate job details.

### Outputs that do not need to come directly from training

These fields may be generated by Backend/API wrapper logic, not by the core training model:

1. `topActionables`
   - Produced by Backend wrapper or deterministic templates.
   - Input: model output (`jobFitAlignment`, `atsFriendliness`, `overallImpression`) plus role/job metadata.

2. `sectionReviews`
   - Produced by Backend wrapper.
   - Wrapper composes CV section review, action points, and user-facing explanations.

3. `jobRecommendations` public detail fields
   - Candidate jobs come from Backend DB.
   - Backend selects candidate jobs by user/role/filter.
   - Model ranks/scores those candidate IDs only.
   - Backend returns job title/company/reason/next step from DB and wrapper logic.

## 2. Expected Production Flow

```text
User uploads or references CV
        ↓
Backend API validates auth, file, ownership, and request payload
        ↓
Backend API loads CV/job/user context from DB/storage
        ↓
Model API runs model-core inference
        ├─ jobFitAlignment
        ├─ atsFriendliness
        ├─ overallImpression
        └─ candidateReranking
        ↓
Backend wrapper adds product-facing copy when enabled
        ├─ topActionables
        └─ sectionReviews
        ↓
Backend DB candidate hydration
        ↓
Backend maps model score + DB details into public recommendations
        ↓
Backend API returns public response
```

## 5. Major Production Gaps

### GAP-01 — Training labels are still weak-label heavy

Historical weak label formula:

```text
fit_score = 0.70 * skill_jaccard + 0.30 * experience_score
```

Problem:

- model can learn a simple heuristic instead of real hiring/job-fit outcome.
- no strong ground truth from recruiter review, application success, interviews, or user feedback.
- model output is hard to claim as business-valid when validation is mostly weak-label based.

Impact:

- `jobFitAlignment.score` may be inaccurate.
- `overallImpression` may become too optimistic or too generic if grounded only in weak signals.

Production requirement:

- define and version label schema v2.
- expand frozen human/recruiter-reviewed validation samples.
- use weak labels only as bootstrap/training support, not the only source of truth.
- report human agreement and slice metrics separately from weak-label metrics.

### GAP-02 — Label distribution must stay healthy

Historical pair distribution was narrow:

- mean around `0.206`
- max `0.5545`
- no high-fit samples

Problem:

- model cannot learn to distinguish strong candidates.
- model scores tend to be low/flat.
- readiness thresholds are hard to calibrate.

Impact:

- `jobFitAlignment.score` is not reliable for the 70–100 range.
- `jobRecommendations` ranking can be weak because the model has not learned strong positives.

Production requirement:

- generate balanced pairs:
  - high-fit positive pairs
  - medium-fit pairs
  - hard negatives
  - random negatives
  - same-role different-seniority pairs
  - cross-role confusing pairs
- ensure every split covers the full score range.
- keep distribution diagnostics in reports/artifacts.

### GAP-03 — Baselines must be beaten, not only met

Historical metric:

```text
MAE      : 0.0844
Accuracy : 0.802 @ tolerance ±0.15
R²       : -0.0038
```

Problem:

- negative R² means the model did not beat mean/median prediction.
- median baseline could reach similar MAE/accuracy.
- gates such as `mae <= 0.10` and `accuracy >= 0.75` are too weak for production claims.

Impact:

- model has insufficient predictive-power evidence.
- `gate_passed: true` is misleading for production readiness.

Production requirement:

- report mandatory baselines:
  - constant mean
  - constant median
  - skill/Jaccard-only
  - cosine-only
  - simple regression baseline
- use stronger gates:
  - positive and meaningful R² for weak-label validation
  - MAE improvement over best baseline
  - ranking metrics such as NDCG/MAP for recommendations

### GAP-04 — Experience feature mapping must be explicit

Historical profile values included:

- `Fresher`
- `1-2 years`
- `3-5 years`
- `5+ years`

Earlier mapping focused on:

- `Fresher`
- `Entry Level`
- `Junior`
- `Mid Level`
- `Senior`
- `Lead`
- `Manager`

Problem:

- `1-2 years`, `3-5 years`, and `5+ years` could silently fall back to default.
- experience signal becomes inaccurate.

Impact:

- weak-fit labels become wrong.
- `jobFitAlignment` and `candidateReranking` become biased.

Production requirement:

- normalize experience before pair generation.
- keep explicit mappings, for example:
  - `Fresher -> 0`
  - `1-2 years -> 1/2`
  - `3-5 years -> 3/4`
  - `5+ years -> 5`
- store mapping in a versioned config artifact.
- report unknown experience rate.

### GAP-05 — Training objective must match CV Analyzer output boundary

OpenAPI/public CV Analyzer behavior needs:

- `jobFitAlignment`
- `atsFriendliness`
- `overallImpression`
- recommendation/reranking support

Problem:

- historical model focused mainly on profile/job embedding fit score.
- `atsFriendliness` was runtime rule-based, not strongly trained/evaluated.
- `overallImpression` was template/rule style, not strongly trained/evaluated.
- CV text extraction and section quality were not part of the original training dataset.

Impact:

- product can look AI-ready while core training does not support all main output areas.

Production requirement:

- separate model tasks:
  - job-fit alignment scorer
  - ATS quality scorer/classifier or deterministic evaluated scorer
  - wrapper-grounded overall-impression signal
  - candidate reranking scorer
- create a real or controlled CV evaluation set with ATS and impression labels.
- keep wrapper-owned prose outside the model artifact.

### GAP-06 — Recommendation training must follow Backend candidate flow

Ideal flow:

- Backend API retrieves candidate jobs from DB.
- Model API only ranks/scores candidate IDs.
- Backend API returns job details from DB.

Historical artifact behavior:

- static `job_index.json` from training dataset.
- static `all_job_embeddings.npy`.
- runtime could rank all jobs in the static artifact.

Problem:

- no guarantee candidates match the latest Backend DB.
- stale job, inactive job, wrong visibility, duplicate source risks.
- model could return jobs that should not be visible.

Production requirement:

- training may produce scoring/ranking model.
- inference input must accept `jobCandidates` from Backend API.
- model output must be limited to model-core fields:
  - `jobId`
  - `matchScore`
  - `matchLevel`
  - `matchedSkills`
  - `missingSkills`
  - `rankingSignals`
- Backend API hydrates title/company/reason/next-step from DB and wrapper logic.

### GAP-07 — Calibration report is required

Problem:

- score `80` is not proven to mean strong candidate fit.
- `successProbability` is not calibrated.
- readiness threshold is not data-backed.

Impact:

- UX may mislead users.
- product decisions based on raw scores can be wrong.

Production requirement:

- produce calibration curves.
- evaluate score buckets:
  - 0–20
  - 21–40
  - 41–60
  - 61–80
  - 81–100
- define score semantics per bucket.
- include calibration in model card and serving artifacts.

### GAP-08 — Data language quality needs explicit evidence

Historical language report:

```json
{
  "EN": 1426,
  "UNKNOWN": 602,
  "MIXED": 23,
  "ID": 22
}
```

Problem:

- EN ratio passed an early gate, but UNKNOWN was high.
- Indonesian product output (`language: id/en`) needs stable ID/EN behavior.
- training text was mostly English; Indonesian CV/job text was underrepresented.

Impact:

- `overallImpression` and wrapper prompts may look good, but model alignment can be biased toward English skill wording.

Production requirement:

- language-specific evaluation.
- normalize skill aliases for Indonesian and English variants.
- add Indonesian CV/job samples.
- report ID and EN separately in readiness evidence.

### GAP-09 — Training reproducibility must remain production-grade

Historical problem:

- main training lived in a notebook without enough production packaging.
- custom layer/module loading was not clearly deployable.
- config, dataset version, code version, and label version were incomplete in model card.

Current policy:

- active training remains notebook-first.
- do not add `training/*.py` execution entrypoints unless workflow is intentionally redesigned.
- release-grade notebooks must be clean-kernel reproducible and produce durable artifacts/reports.

Impact if not maintained:

- retraining becomes non-deterministic.
- Model API may fail to load artifacts.
- model-version audit becomes difficult.

Production requirement:

- keep one final training notebook reproducible from a clean kernel.
- keep custom TensorFlow components serializable and registered.
- model card must include:
  - git commit
  - dataset hash
  - label version
  - split seed
  - feature config
  - baseline metrics
  - artifact hashes
- optional package extraction can be added later only when all path/test references are updated.

### GAP-10 — CV parser/evaluator must be part of validation evidence

Current Model API runtime parses PDF and applies deterministic ATS evidence/penalties.

Problem:

- parse failure must be evaluated on realistic CV formats.
- ATS score must be tested against format variety.
- model/wrapper quality depends on whether text extraction is valid.

Impact:

- `atsFriendliness` can be wrong if parser fails.
- `overallImpression` can be poor when input text is empty or partial.

Production requirement:

- build CV parsing benchmark covering:
  - normal PDF
  - scanned/OCR fallback policy
  - multi-column PDF
  - table-heavy PDF
  - DOCX or unsupported-format policy
  - short CV
  - long CV
  - Indonesian CV
  - English CV
- metrics:
  - extraction coverage
  - section detection accuracy
  - ATS issue precision/recall
  - empty-text rate

### GAP-11 — TensorFlow delivery must satisfy `REQUIREMENT.md`

Context:

- Phase 12–24 improved production evidence: snapshots, feature builder, pair generation v2, E5 runtime, human validation, ATS benchmark, reranking fixtures, calibration, contract validation, and final-gate evidence.
- `REQUIREMENT.md` requires TensorFlow Functional API or Model Subclassing, a custom component, custom training/evaluation loop with `tf.GradientTape`, TensorBoard logs, export as `.keras` or `SavedModel`, inference code, REST API, and GenAI as a secondary feature.

Legacy context:

- `legacy/bisakerja_model_training_FINAL.ipynb` was closer to some TensorFlow-format requirements because it used TensorFlow, custom component context, TensorBoard, `.keras` export, inference helper, and FastAPI/GenAI prototype context.
- Legacy was still not enough for production because it relied on older weak labels, `all-MiniLM-L6-v2`, poor high-fit distribution, prototype API/runtime, and did not satisfy all current custom-loop/evidence expectations.

Problem:

- audit evidence and TensorFlow delivery must stay consolidated in the final production notebook.
- a trained `.keras` file alone is not enough.
- serving an artifact without reload smoke, TensorBoard evidence, model card, and manifest evidence is not acceptable.

Impact:

- repository could look production-ready from reports while failing requirement review.
- Model API could use artifacts that do not match the deployment target.
- training evidence can become scattered and hard to review.

Production requirement:

- keep `training/notebooks/phase_25_tensorflow_training_delivery.ipynb` as the final TensorFlow delivery notebook.
- notebook must use TensorFlow Functional API or Model Subclassing.
- notebook must include at least one custom layer/loss/callback.
- notebook must use custom training/evaluation loop with `tf.GradientTape`.
- notebook must write TensorBoard logs.
- notebook must export `.keras` or `SavedModel`.
- notebook must keep current production contract: `pairs_v2`, E5 `intfloat/e5-base-v2`, normalized embeddings, anti-leakage splits, human validation, ATS benchmark, calibration, model card, artifact manifest, and Model API handoff fixtures.
- production-ready status must fail if export comes from dirty/unverified state, notebook stores error output, TensorFlow artifact cannot reload, TensorBoard logs are missing, or strict baseline/score-band gates are not satisfied.

## 8. Suggested Gates Before Production

Minimal gate for model v2:

```text
Job-fit / jobFitAlignment:
- MAE improves >= 20% vs best baseline
- R² >= 0.15 on weak-label validation, or documented stronger human-label alternative
- Spearman >= 0.35 for pair ranking
- human validation agreement >= 0.65 weighted kappa or equivalent

ATS Friendliness:
- issue detection precision >= 0.75
- issue detection recall >= 0.65
- score bucket agreement >= 0.70

Job Recommendations:
- NDCG@10 >= baseline + 15%
- no unknown jobId returned
- no duplicate jobId returned
- all returned jobId values must come from Backend candidate set

Robustness:
- CV parse empty-text rate < 5% on supported PDF/DOCX benchmark
- ID and EN evaluation reported separately
- TensorFlow artifact reload smoke passes
- Model API live smoke passes with real runtime dependencies
```

### P2 — Quality improvement

1. Learning-to-rank objective for recommendations.

4. Periodic retraining pipeline.
5. Larger anonymized candidate-set relevance evaluation.

## 10. Final Assessment

Historical model training was acceptable for **prototype/demo**.

Production-track work has improved structure, evidence, TensorFlow delivery, and Model API handoff. However, production score-quality claims still depend on stronger validation evidence and complete release gates.

Training is not fully production-ready unless these risks are closed:

- model must beat meaningful baselines.
- labels must be stronger than narrow weak labels.
- high-fit samples must be represented.
- training objective must match Model API output boundary.
- recommendation flow must rank Backend-provided candidate IDs only.
- ATS and overall-impression behavior must be evaluated as production tasks.
- TensorFlow artifact must reload and serve through Model API smoke tests.

Recommended direction:

- keep core model focused on `jobFitAlignment`, `atsFriendliness`, `overallImpression`, and candidate reranking.
- keep Backend wrapper responsible for `topActionables`, `sectionReviews`, auth, persistence, and job hydration.
- keep Backend source outside this model repository.
- use exported Backend contract snapshots or release fixtures from <https://github.com/bisa-kerja/bisakerja-api> only when contract validation is needed.
